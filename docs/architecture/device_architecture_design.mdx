# 设备架构设计

设备层把平台硬件操作包装成服务可以使用的设备对象。它的职责是提供设备操作入口、保存设备状态，并让平台实现能够在初始化时注册操作。

## 当前设备类型

当前设备抽象包含显示器、电源、电池、时间、传感器、扬声器、麦克风和振动器。显示器、电源、电池、时间、扬声器、麦克风和振动器通过各自的 `get_instance()` 访问单例；传感器可以按名称或类型查找，并为每种类型记录默认实例。

所有设备都使用 `DEV_STATE_NONE`、`DEV_STATE_READY`、`DEV_STATE_BUSY` 和 `DEV_STATE_ERROR` 表示设备层状态。状态值描述设备抽象是否可用，不等同于业务服务状态。

## 注册与状态

平台实现需要在服务使用前注册对应的操作表。例如显示设备注册 `set_brightness`、`power_on` 和 `power_off`，时间设备注册 `get_datetime`，传感器注册名称、类型和传感器操作。注册函数会检查必要操作；重复注册通常返回 `EOS_ERR_ALREADY_EXISTS`。

设备驱动可以通过对应的 `report_state` 接口更新设备状态。设备层不会为所有设备提供完全相同的注册/注销 API，也没有统一的“设备管理器业务接口”；具体操作以该设备公开头文件为准。当前实现没有通用设备注销流程。

## 服务边界

应用和脚本不应直接使用设备层。服务负责采样周期、缓存、配置持久化、播放状态、休眠策略等业务行为，再调用设备操作。这样可以让设备实现只关心平台操作，同时让服务在 Native、WASM 或其他移植中保持相同的上层语义。

传感器服务尤其区分设备上报和应用读取：驱动把数据提交给服务，服务维护每种类型的 FIFO、最新值和订阅通知；应用通过 `eos_sensor_read*` 或订阅接口获取数据。

## 面向移植的要求

移植平台时应为所支持的设备实现必需操作，并在系统服务初始化前完成注册。无法提供的硬件能力应通过设备状态、能力查询或服务返回码体现，不能在服务层假定所有设备都存在。WASM/Native 模拟器的设备实现是平台模拟，不代表实际硬件的性能或可用传感器集合。
