# Writing Tests

When adding new tests to ElenixOS, the first decision is whether the verification requirements should go through the framework layer pipeline or build a standalone GUI page. These two paths serve different verification goals and differ in execution model, result determination, and integration approach. Understanding the applicable scenarios for each and the framework layer's internal workflow is a prerequisite for ensuring test consistency and maintainability.

## Choosing a Test Form

For regression verification of deterministic API results, boundary conditions, and error paths, use the synchronous test framework. When continuous rendering, user interaction, real time passage, or hardware feedback is required, use a standalone GUI page in the test app.

## Synchronous Test Contract

Test functions are called in the LVGL main loop context and must complete verification and record results before returning. Do not block or wait in tests, and do not treat "test has started" as a pass; cross-frame scenarios should be rewritten as conditions that can be checked in a single call, or use a standalone interactive page.

Test result recording follows the framework's current recording rules. After one execution, subsequent asynchronous callbacks cannot reliably overwrite an already-completed test result.

## Naming and Registration

Test names must be unique. The current GUI groups by prefix in the name; keeping tests in the same group using a consistent prefix is sufficient to place them in the same group. Registration should be completed before the test page is created, and added to the runner through the corresponding subsystem's test registration entry.

## Resource Cleanup

Activities, LVGL objects, timers, subscriptions, and files created by tests should be cleaned up when the test ends or the page is destroyed. Activity/View deletion may cascade-delete child objects; tests should not continue using old pointers after deletion. Tests that need to run multiple times should also restore global state to a repeatable initial condition.

## Interactive Pages

For scenarios that cannot be determined in a single synchronous call, such as UI, sensors, and audio, a standalone Activity page can be created, with the page lifecycle managing objects and subscriptions. Standalone pages are responsible for displaying results and are not automatically included in the framework layer's pass/fail aggregation.

## Capacity and Configuration

The test app is controlled by `EOS_ENABLE_TEST_APP`. There are compile-time limits on the number of test entries and groups; when approaching the limit, merge duplicate scenarios or adjust the build configuration rather than assuming the registry will dynamically expand.
