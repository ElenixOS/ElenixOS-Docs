# UI Components Module

ElenixOS UI is built on LVGL, but UI ownership and hierarchy are jointly constrained by Activity, the top-layer registry, and the system UI manager. Components are not an arbitrary collection of LVGL objects.

## UI Model

Activity owns the application page View; system-level components use semantic top-layer slots. A slot corresponds to a permanent container and expresses the hierarchical relationship of application content, page snapshots, application headers, global interaction, system UI, modal UI, secure UI, and debug UI. Slot numbers are ordering semantics, not LVGL child indices, and cannot be persisted.

The message list, control center, and other sibling overlays share the interaction slot. Foreground objects and touch objects within a slot are reordered through a unified focus mechanism, avoiding each component separately seizing the top layer. Modal, lock screen, error, and permission UI reside at specified higher layers.

## Responsibilities

- Activity manages page Views, page transitions, and page destruction.
- The Overlay layer manages system-level containers and stable visual hierarchy.
- The Interaction slot manages the current focus and input objects of sibling interactive overlays.
- Components are responsible for their own internal objects and callbacks, but not for deleting shared slots, Activity Views, or the root objects of other components.
- Scripts create objects through the registered `lv`/`eos` APIs; script handles remain bound by the owning View and program lifecycle.

## Input and Rendering Flow

Input devices do not share a single event queue that can make decisions on behalf of all inputs. Platform touch is handed to the touch input layer via the LVGL pointer indev, and then hit-testing and widget event dispatch are performed by the LVGL object tree. The crown knob is bound to the currently scrollable object; the crown button and side button are first converted into system actions, then dispatched by the main loop to Chrome or power management. The foreground relationship of pages and overlays is managed by Activity/Chrome, not inferred by drivers.

Therefore platform ports should report standardized touch, knob, or button states; page navigation, wake-up, opening the control center, and widget interaction are still handled by the system layer. UI callbacks execute in the LVGL/runtime main loop; rendering output is carried by the platform display port.

## Message List and Notification Boundary

The message list is a UI component placed in the shared interaction slot, responsible for displaying list items and details. The current implementation has no general notification broker, notification persistence service, or JS-facing notification delivery API. The `notification` permission category and its settings entry do not by themselves constitute a notification sending/storage contract; this list UI should not be regarded as the owner of a notification service.

## Architecture Constraints

- System components must use semantic top-layer slots and must not rely on the current child index or privately reorder the shared top layer.
- Sibling overlays must obtain focus through the interaction slot; system modal layers, lock screen, and error layers must not be covered by ordinary application overlays.
- Cascading invalidation caused by parent object deletion must be treated by components and script handles as a normal lifecycle outcome.
- Objects managed by Activity/Recent Apps/system overlays can only be released by the corresponding owner; components must not delete root objects across owners.
- UI and SNI callbacks must return quickly and must not block or directly operate LVGL from non-UI threads.
