# LVGL UI API

Scripts use the LVGL classes registered in the current runtime through `lv`. Object constructors receive a parent object; the page root object usually comes from `eos.view.active()`.

```js
const view = eos.view.active();
const button = new lv.button(view);
button.setSize(180, 64);
button.align(lv.ALIGN_CENTER, 0, 0);

const label = new lv.label(button);
label.setText("Hello, ElenixOS!");
label.center();
```

## Currently Exported Classes

The classes currently registered in the runtime are: `obj`, `button`, `label`, `arc`, `bar`, `screen`, `color`, `timer`, `anim`, `buttonmatrix`, `calendar`, `chart`, `canvas`, `checkbox`, `dropdown`, `image`, and `imagebutton`. Among these, `screen` and `color` are static utility classes, while `obj`, the widget classes, `timer`, and `anim` are used according to their respective constructors.

Class names in the complete LVGL documentation do not automatically constitute the ElenixOS JS API; scripts may only use registered classes. Specific methods and properties are subject to the current page and bindings.

## Objects, Layout, and Styles

Generic objects provide operations for position, size, alignment, parent-child relationships, flags, events, and deletion; for example, `setPos`, `setSize`, `align`, `setFlexFlow`, `addFlag`, `addEventCb`, and `delete`. Widgets then provide their own properties, such as `label.setText` or `bar.setValue`.

```js
const panel = new lv.obj(view);
panel.setSize(300, 100);
panel.setFlexFlow(lv.FLEX_FLOW_ROW);
panel.setStyleBgColor(lv.color.hex(0x202020), 0);
```

The actual entry point for the color utility is `lv.color.hex(number)`. Layout constants, directions, events, styles, and widget constants are exported as `lv` root constants, but the available set of constants comes from the current bindings, not from all the macros of native LVGL.

## Events

```js
button.addEventCb((event) => {
    eos.console.log("Button clicked");
}, lv.EVENT_CLICKED, null);
```

Objects also provide `removeEventCb`, `removeEventCbWithUserData`, and `sendEvent`. Event callbacks execute synchronously in the LVGL runtime context, and blocking will delay other work in that context. After a widget or parent object is deleted, the related callbacks and script handles become invalid accordingly.

## Resource Lifecycle

Objects created by scripts are usually managed along with the parent object tree; `timer` and `anim` are independent script resources. When an Activity/View is destroyed, the program stops, or the engine resets, the related resources are cleaned up by the runtime. Scripts should use the deletion interfaces provided by objects when they are no longer needed, and should always avoid retaining handles that have already been deleted.
