# Runtime

The runtime combines platform initialization, system services, Activity pages, and script programs. It is not a thin wrapper for "scripts calling C functions," but rather a lifecycle coordination layer for programs, Realms, pages, and native resources.

## Runtime Model

At startup, platform display/input and device registration are established first, then system services are initialized, and finally the root Activity, script runtime, and applications/watchfaces are started. When platform capabilities are insufficient, this is expressed upward through device state, capability queries, or service return codes; the startup process must not assume that all platforms provide the same capabilities.

Script programs, Activities, and Views are three distinct ownership layers:

- SPM owns script programs, JavaScript Realms, SNI contexts, and script callbacks.
- The Activity controller owns the page stack, root Activity, page Views, and transitions.
- LVGL owns child controls in the object tree; deleting a parent object may cascade-delete them.

SPM is the sole entry point for the script program lifecycle. Upper-layer application/watchface managers **are prohibited from directly calling `script_engine` to start applications or watchfaces**, and must not bypass SPM to operate the Script Engine Core; starting, resuming, suspending, and stopping must all be done through SPM's application/watchface management interfaces. Only one unterminated program instance is allowed per application ID; the instance ID links the program, Activity, and Recent Apps record together.

## Program and Page States

Program states are `ACTIVE`, `SUSPENDED`, `STOPPING`, or `TERMINATED`. Suspension means the program can still be resumed, typically preserving the Realm, page sub-stack, and Recent Apps snapshot; only eviction, uninstallation, root watchface replacement, or a fatal engine error leads to a full stop.

Activities use their own page states and exit policies. Page transitions explicitly choose to preserve, destroy, or park, rather than letting the caller modify a long-lived destroy/suspend flag. Ordinary Activities cannot be directly destroyed by arbitrary callers; the root Activity is managed by the root replacement process.

## Callbacks, Execution Context, and Engine Reset

SNI callbacks record the owner program and engine generation. Before entering a callback, it must be confirmed that the program is still active, the context is not suspended, and the generation has not changed; the owner Realm is entered before calling JS. After an LVGL object is deleted or the engine is reset, old callbacks, old handles, and old native pointers all become invalid.

A fatal engine error saves the error context, destroys the affected SPM program and cleans up the Recent Apps entry, and then the Script Engine Core rebuilds the JerryScript heap within the current OS process. A Core rebuild does not mean that all crashed programs automatically restart: Applications and JavaScript Watchfaces enter the error-handling/user-restart path; Console fatal automatically rebuilds the Watchface and restarts the previous script application according to recovery conditions. Old pages, Views, and JS objects become invalid with the old engine generation; for the capture and rebuild order and the recovery paths for each type, see [Script Engine Overview](./script_engine_overview).

## Threading and Invocation Constraints

The runtime main loop executes Activity/LVGL operations, LVGL timers, and the SNI/JS callbacks dispatched by those timers. The `main.js` of a newly started application is executed synchronously by SPM, which occupies the main loop call that initiated the start; the loading screen does not let the script run in parallel.

The Event Bus itself does not switch threads or queue: `eos_event_post` synchronously invokes subscribers in the publisher's context. Sensor `eos_sensor_notify` also synchronously invokes Native subscribers in the publisher's context; Battery data changes emit events synchronously within the `eos_battery_report_raw` call stack. They cannot all be treated as GUI main loop callbacks. If a platform ISR/device thread wants to trigger a chain that may access LVGL, the file system, or scripts, it should first defer to the appropriate context through the Dispatcher or the target Service's thread-safe entry point; data passed across threads must be copied or kept valid before being queued.

Even if a callback is dispatched by a timer/Dispatcher, it still executes synchronously within the Core call stack and should be short and non-blocking. Only the callback's explicit scheduling boundary can indicate which context it runs in; asynchronous or thread-safe behavior cannot be inferred from the name `callback`.

## Runtime Constraints

- After an Activity/View is destroyed, all related C pointers and script handles must be considered invalid.
- Script resource release must be performed by the owning SPM/SNI context; applications cannot bypass system resource lifecycle through JS reference counting.
- When a program is suspended, its timers, animations, and script callbacks are paused or resumed according to the Recent Apps recovery policy; no arbitrary JS continues to execute while suspended.
- New callbacks must be bound to an explicit owner, generation, and cancellation/deletion path; ownership cannot be guessed from a global current-program.
