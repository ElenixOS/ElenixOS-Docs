# Application and Framework Contract

This page defines the system boundaries that application and Framework developers can rely on. Built-in C applications in the system work through Activities, services, and UI components; script applications use EPKG identity and can only access the Core through the`eos`/`lv`interfaces exposed by SNI. Neither can hold Vendor drivers or device operation tables. SPM only owns the program and Realm lifecycle of script Applications/Watchfaces, and is not the unified entry point for the lifecycle of all built-in C pages.

## Launch Identity and Running Instance

The`manifest.json`ID of an installation package is the application/watchface identity. Launch requests target this ID, not a file name or display name. The application manager is responsible for validating the installed identity and handing the request to SPM; SPM exclusively owns the Script Engine Core and Realm lifecycle. Only one unterminated script program can exist for an ID at a time: foreground switching typically resumes an existing instance and cannot start a second Realm.

Package installation starts from a single EPKG context: reading metadata can be used for preview; installation must also fully validate all entries, then unpack according to`package_type`and update the installation identity. A successful preview, completed transfer, or the existence of a package file does not equal successful installation; the caller should use the installation result and events to determine the final state.```mermaid

Program resumption reuses the same instance and Realm saved by Recent Apps, does not re-execute`main.js`, and does not create duplicate parallel copies. Watchfaces use the root Activity replacement flow, with the watchface manager completing the program switch via SPM.

Page transitions and program lifecycle are two different things. An Activity can pause or destroy a page while retaining the program; when Recent Apps suspends, the program and some resources may still exist; only eviction, uninstallation, root watchface replacement, or a fatal engine reset enters a full stop. Applications must not directly call`script_engine`to start, resume, or clean up script programs.

## Capability Consumption Model

| Capability | Application-side interaction | Validity and end responsibility |
|---|---|---|
| Sensor (Native Core) | Pull FIFO/latest, or Push subscription callback; when there is a sampling demand, the service arbitrates. | latest returns invalid/not found when there is no sample; a zero value can still be valid. Callback parameters are only borrowed during the synchronous notification; Native subscriptions should be cancelled by the registering owner when no longer in use. |
| Sensor (JS) | There is currently no raw Sensor subscription interface; you can read the`eos.sensor`cache, or use`eos.metric`semantic values. | Metric samples carry`valid`/`stale`; subscriptions are bound to the program SNI context, and it is not guaranteed that each callback triggers one hardware sample.`eos.sensor.setSamplePeriod`uses a single compatibility demand per type, not a demand isolated per script/application; multiple callers will share and update it. |
| Battery | Native Pull current snapshot, or subscribe to change events; Metric provides semantic battery level values. | Invalid until a valid report is received; percentage/charging events are triggered by threshold changes, not broadcast on every hardware sample. |
| Metric | Pull once, or periodically notified by SNI timer. | SNI saves the owner program/generation; JS will not be called when the program is inactive, and unsubscribing or context cleanup releases the subscription. Destroying an Activity alone does not automatically mean the program is destroyed; data demands that are no longer needed should be actively cancelled by the application. |
| System events (Native Framework) | C modules can subscribe to state changes such as installation, power, and pages. |`eos_event_post`is a synchronous broadcast, and parameters are borrowed during the callback; to retain data after the callback returns, it must be copied. Unsubscribing is the responsibility of the subscribing module. Currently JS has no general Event Bus API and can only use the various registered dedicated callback interfaces. |
| Permission requests | JS requests are completed asynchronously by the authorization UI, and the result is returned via a script callback; Native services return the authorization status. | Requests may be denied, queued, or unable to call back due to an invalid program context; initiating a request itself does not mean authorization has completed. |
| Audio | Playback/recording requests synchronously return whether startup succeeded; PCM supply and hardware output then continue. | Speaker and microphone capabilities are independent; there is currently no general JS playback completion callback contract. Playback resources are held by the service, and the application stops or pauses through the service. |
| Time | Service synchronously Pulls the platform date and time. | Core has no clock update Push stream or unified time-sync completion event; the timezone/time-sync source belongs to the platform. |
| Display / Power | Framework requests brightness, sleep, AOD, or wakeup; power state changes are observed via synchronous system events. | Software state does not equal physical hardware confirmation; some operations are void/fire-and-forget, and specific platform capabilities may be missing. |
| Haptics | Framework requests feedback intents such as tick/buzz/long-vibration. | Device operations have no return value, and there is currently no per-vibration completion/failure event; the application cannot confirm that physical feedback has occurred. |
| Files and configuration | File/JSON operations are synchronous path operations;`eos.config`uses the current script ID to construct the application/watchface configuration file. | Handles become invalid after closing, and dynamic values are released according to the owning API. The general Storage API does not automatically isolate paths based on script identity, and a path prefix itself does not constitute a sandbox. |
| State / Log | State is synchronous reading and updating of persistent state; Log receives formatted messages via a listener. | The log listener executes synchronously and the message buffer is only valid within the callback; system state is not application configuration; logs have no background queue guarantee. |
| Notifications | There is currently no general application notification delivery API, notification broker, or persistent queue. | The`notification`permission category and message list UI do not mean that applications can publish/read system notifications. |

Metric currently has one visible validity exception:`battery.charging`folds the Battery Service's invalid/uninitialized state into`false`and still marks it as valid. If JS needs to determine whether a battery reading exists, it should also check`battery.percent.valid`; Native can use the Battery State validity query. This behavior is a current implementation limitation, not a general rule for all boolean Metrics.

Native Sensor's Push callback executes synchronously in the context that calls`eos_sensor_notify`; if the Vendor enters notification from an ISR, all consumers will also execute in that context. Therefore the platform should publish in a task/main loop context where Core callbacks can be safely executed; interrupts should only collect/queue unless the entire downstream path is explicitly safe to run in an ISR. JS metric callbacks are dispatched by the LVGL timer in the Core main loop and enter the owning Realm.

## Cleanup of Pages, Programs, and Callbacks

- An Activity owns the page View; deleting the View invalidates its LVGL child objects, tree-node handles, and page callbacks. Old View pointers must not be saved and used across destroy or root replacement.
- SPM owns the script program, Realm, and program-level SNI context. Stopping/resetting invalidates all JS handles and callbacks of the old generation; SNI re-validates the owner, state, and generation when the callback enters.
- Activity pause and SPM suspend are not equivalent. While the program is retained by Recent Apps, script-subscribed objects may still be alive; when hardware/service demands need to be stopped, they should be explicitly cancelled or released in the lifecycle callback.
- Native callback`user_data`, event`param`, and synchronously passed data pointers are managed by the subscriber according to the contract; the system will not automatically discover and unregister arbitrary C pointers merely because an Activity is destroyed.
- Timeout, no device, unauthorized, no sample, and script exception are different results. Applications should branch on result/status/validity fields, and must not infer success from zero, an empty object, or a callback that did not occur.

## Boundaries Application Development Should Not Bypass

- Use the Activity Controller to manage pages; do not directly modify the Activity stack, delete system-managed Views, or reattach parked pages.
- Use services or registered SNI interfaces to access sensors, audio, storage, power, and display; do not rely on device lookup order or Vendor implementation details.
- New JS APIs can only be exposed through SNI descriptions and owner-bound callback/resource paths; do not expose raw native pointers.
- EPKG preview is only suitable for displaying metadata and cannot replace full validation and installation results.
