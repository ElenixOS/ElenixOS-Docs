# Application Management Module

The application management module is responsible for the identity, discovery, installation, uninstallation, ordering, and launch coordination of installed applications. It does not own script Realms, nor does it directly drive Activity pages; these responsibilities belong to SPM and the Activity controller respectively.

## Application Model

Applications and watch faces use the same EPKG v1 container. The `package_type` in the package header determines installation dispatch, and the `id` in `manifest.json` is the stable key for runtime identity, installation directory, and Recent Apps. Application management completes preview, manifest reading, full validation, and unpacking through a unified package context. For the internal layout and field semantics of the installation package, see [EPKG v1 Installation Package Format](../../package_format); for the official project and packaging workflow, see [ElenixOS-Toolkit](../../../development/toolkit).

The installation process sequentially reads metadata, checks the API level and package type, fully validates the EPKG, unpacks to an installation directory named by ID, and updates the discovery results and ordering state. Preview only provides metadata and does not constitute full validation. Installation success or failure is expressed through result codes and system events; whether a directory appears is not used as the criterion for installation result.

## Installation and Uninstallation

When installing an application with the same ID, the existing installation content is handled according to replacement semantics; the application ID must not change due to a change in the package file name. Uninstallation must simultaneously handle the installation content, application data, and permission records, and publish an uninstallation event; after a successful installation, publish an installation event.

Package parsing, decompression buffers, manifest temporary information, and installation target paths each have independent release responsibilities. After closing the EPKG context, its header, file table, or file handles must not continue to be read.

## List, Ordering, and Launch

The application list is rediscovered by installation directory, and the ordering sequence is saved by the `app_order` configuration; uninstalled IDs are no longer valid ordering entries. Application management is responsible for stable identity and ordering, not for creating Activities or deciding page exit policies.

When opening a new script application, the application manager first establishes and enters the App Activity that hosts the loading UI, then requests SPM to synchronously run the script; `main.js` establishes the page content in the startup call stack. After a successful return, the Activity binds the program instance ID and engine generation. Recent Apps restoration reattaches the same instance without creating a parallel Realm. **Directly calling `script_engine` to launch an application is prohibited**.

## Programs and Recent Apps

When an application leaves the foreground, the Activity controller first detaches the application Activity sub-stack; Recent Apps then parks the program and page as `SUSPENDED`, or performs a full destruction. Recent Apps entries bind to the program instance ID and may save snapshots for return animations. After reaching the count or memory watermark, the system evicts entries through the per-instance stop path, while cleaning up the corresponding program and associated state.

Suspension retains the program instance and is not equivalent to exit. Sensor requirements, audio, timers, animations, and script callbacks are handled according to the program suspend/resume policy; resources that continue to be retained have explicit owners and recovery paths.

## Architectural Constraints

- The application ID is a stable key; package paths, display names, or package file names must not be used in its place.
- SPM is the sole owner of the script program lifecycle; the application manager must not directly operate the Script Engine Core, nor directly call `script_engine` to launch an application.
- Two unterminated script programs with the same application ID must not exist simultaneously.
- The cleanup of Activities, Recent Apps, and SPM must be completed as a set, and must not produce "Recent Apps entries without a program" or "script programs still referencing an old View".
- The current format only accepts EPKG v1; the legacy EAPK/EWPK compatibility paths and the installation flow distinguished by magic are deprecated.
