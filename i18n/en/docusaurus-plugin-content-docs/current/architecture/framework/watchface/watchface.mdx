# Watchface System

The watchface is the system's root page. Both the built-in watchface and JavaScript watchfaces are displayed through the root Activity and are not pushed onto the Activity stack as ordinary pages; their scripts and Views are still managed by their respective runtime lifecycles.

## Watchface Model

Current watchface installation and application installation share EPKG v1. The package header's `package_type` must be Watch Face, and the manifest's `id`, API level, and permission declarations determine runtime identity and compatibility. The watchface manager should not maintain a second set of package parsing or unpacking logic. For the in-package structure, see [EPKG v1 Package Format](../../package_format); the Toolkit can build existing watchface projects, but currently does not provide Watchface project initialization, see [ElenixOS-Toolkit](../../../development/toolkit) for details.

The watchface list includes the built-in fallback watchface. The fallback watchface is a system resource, not an installable item that can be uninstalled like an ordinary package; only installed JS watchfaces come from the watchface installation directory. The default watchface ID is determined by system configuration.

## Switching and Lifecycle

The watchface manager coordinates watchface switching through SPM's start, resume, and stop flows, and replaces the root Activity; its call boundary with `script_engine` is managed by SPM. The old watchface's Activity, View, script Realm, SNI callbacks, and watchface components all become invalid during the replacement flow. After switching completes, the caller re-acquires the current root object from the root Activity interface; the old root pointer becomes invalid with the replacement.

When opening an application, the current JS watchface can enter a suspended state; when returning to the watchface, the same program instance is resumed. Switching watchfaces, uninstalling watchfaces, Recent Apps eviction, or engine reset all perform a full destruction, and the old watchface no longer exists as a resumable page.

## Data, Components, and Page Ownership

JS watchfaces use `main.js` as the entry point and create pages through the system interfaces exposed by SNI. The Activity/View determines the lifecycle of the page and the LVGL object tree; the watchface script does not own the root Activity.

Data and drawing components are two distinct extension boundaries. `eos.metric` maps existing service state to semantic values; `eos.ww` exposes reusable native LVGL watchface controls to scripts. A component can bind to an existing Metric, or the script can pass read results into the component. In this way, components focus on presentation, while data services focus on units, validity, expiration state, and source.

Metric currently uses static semantic mapping and has no dynamically registerable Provider plugin model. Adding a new watchface component that consumes an existing Metric does not require changing the sensor or Metric service; adding new semantic data requires extending the Metric mapping and SNI exposure. If the data comes from new hardware, it should first pass through the corresponding device/service boundary, and watchface components should not access drivers directly.

The LVGL handles returned by watchface components belong to their parent View and the root Activity; when the object tree is destroyed, the component's timers, callbacks, and internal resources must also become invalid in sync. The resources accessible to scripts are still limited to the interfaces registered with SNI, and after the root Activity is replaced, all old handles expire.

## Architecture Constraints

- The watchface is the root Activity and must not fake a second root page through the ordinary page stack API.
- Watchface start, resume, and stop are all managed by SPM; the watchface manager does not directly call `script_engine` to create or start a script context.
- Watchface switching must handle the ownership of the root Activity, View, script program, and watchface-specific components simultaneously.
- The built-in fallback watchface cannot be deleted as an ordinary installable package, and the configuration must not point to a watchface ID that no longer exists.
- Watchface packages must first pass complete EPKG v1 validation before unpacking and loading scripts; a successful preview does not mean it is runnable.
- New code should use root Activity semantics to access the current watchface and should not rely on deprecated dedicated getters.
