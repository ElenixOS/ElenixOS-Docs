# Log Service

The log service filters by severity level and dispatches formatted messages to registered listeners. The system provides four levels: debug, info, warning, and error; the global minimum level determines which messages are dispatched.

Listeners are responsible for their own lifecycle. System listeners cannot be unregistered like ordinary listeners; deactivating a listener does not remove the registration. Listener callbacks should return as quickly as possible, and the message buffer is only valid during dispatch—if it needs to be retained long-term, the receiver must copy it.

Log tags are used to identify the source of a message. The platform can provide listeners such as standard output; whether color output is enabled is determined by the build configuration.

The Core log level defaults to `DEBUG` at startup, so DEBUG, INFO, WARN, and ERROR all pass level filtering. The Simulator project enables the stdout listener by default, and Native startup logs are also written to the Simulator's `tmp/latest.log`; if a target platform does not register an output listener, logs are still filtered by level but will not be automatically written to a serial port or file. The Simulator accepts at most 8 listeners; when slots are exhausted, `eos_log_register_listener()` returns `-1`. `EOS_LOG_ENABLE_STD`, `EOS_LOG_MAX_LISTENERS`, and `EOS_LOG_USE_COLOR` can be adjusted via the Logging group in Kconfig; the minimum level can also be changed at runtime using the log API.

The Core first filters by global level, then synchronously invokes listeners; the message memory received by a listener is only valid during the callback. The platform output backend is a log listener, not an application storage or notification service. If a sink requires time-consuming I/O, it should copy the needed content in the listener and queue it itself; see [Context Differences of the Event Bus](../../kernel/event/events).
